# 时间轴缩略图：方案与实现

目标：视频一开始播，后台就把整条进度条的预览图做出来存在本机；鼠标在进度条上怎么扫，图都立刻出来，
而且永远不为了一张图去打扰主播放器。

代码在 `thumbnail/`（引擎，不认识网盘、不依赖 Compose），接线在 `shared` 的 `PikoMediaRepository.openThumbnailStreams`、
`desktopApp` 的 `PikSeekRuntime`，界面在 `ui` 的 `TimelinePreview.kt`。

## 结构

```
主播放器（MediaMP 的 mpv）── 只管播放，从不为缩略图定位
        │ 出了第一帧
        ▼
ThumbnailEngine.Session
   ├─ 本机缓存有没有？ 有 → 读雪碧图，完。不建解码器、不查网盘、不发请求
   └─ 缺的才生成
        ├─ 画面来源（按顺序试，前一个整个用不了才换下一个）
        │    1. 低清晰度转码流（TsSliceSource）
        │    2. 原画经本机代理（SeekingSource）
        │    或：本机副本（SeekingSource）
        ├─ 取帧：另一个 mpv 实例，无画面、无声音、软件解码（MpvFrameGrabber）
        ├─ 调度：先当前位置附近，再粗略铺满，再补全（ThumbnailPlan）
        └─ 存盘：WebP 雪碧图 + index.json（ThumbnailCache）
```

悬停时界面调 `Session.frameAt(时刻)`：在内存里按时刻找最近的一帧，立刻返回。**这条路上没有任何网络与磁盘读取。**

## 顺序是硬规矩

用户点视频 → 取流 → 交给主播放器 → **第一帧** → 这时才开缩略图会话。

`PlayerScreenState.hasFirstFrame` 为真之前，`VideoPlayerWindow` 不会调 `openSession`；缓存检查、解码器、查转码流都在它之后。
换清晰度、断线重连不会让预览重来（集没换）。

## 画面来源

### 1. 低清晰度转码流（首选）

PikPak 给视频配了几档转码（常见 480P、720P、1080P）。缩略图只有 240 像素宽，挑**不低于 360P 的最低一档**：
同一帧要读的数据比原画少得多。

转码流是 MPEG-TS，没有索引，让解码器在里面定位要二分查找、一次十来处跳读。所以不让它定位（`TsSliceSource` + `TsScan`）：

1. 按「时刻 → 字节」的对照估一个位置。起初只知道片头在 0、片尾在末尾，按比例估；
2. 从那里往后一块一块读，找第一个关键帧（看 TS 包的随机访问标志；没有标志时看帧开头是不是 IDR / 参数集）；
3. 读到这一帧结束（下一帧的第一个包），把这一帧的视频包截出来，前面放上 PAT、PMT，写成一个只有一帧的小 TS 文件；
4. 解码器打开这个本机小文件，取出画面，文件删掉；
5. 关键帧自带真实的时间戳：记下「这个时刻 → 这个字节位置」。后面的估计在已知的点之间插值，越来越准。

每张缩略图记的是**那一帧真实的时刻**，不是要它的那个时刻。悬停时按真实时刻找最近的，所以图与时间对得上，
哪怕转码流的码率不恒定、起初估偏了十几秒。

读取对齐到 SDK 的块（256 KiB）：SDK 按块取数据，碰到块里一个字节整块都下回来，不对齐的话一次读取会跨两块、多下一倍。

读取用 SDK 的后台优先级（`StreamRole.BACKGROUND`）、不预读。主播放器要连接时，SDK 自己就让后台读靠后。

### 2. 原画（转码流用不了时）

没有转码、转码不是 TS、或者前几帧都取不出来时，换成原画：解码器经本机回环代理（后台优先级）打开原文件，
用 mpv 的关键帧定位。MP4 / MKV 有索引，定位只读索引指的那一小段。原画码率高，每帧的数据量比转码流大。

### 3. 本机副本

播放的是下载好的文件时，直接对文件做关键帧定位。实测很快（见 `BENCHMARK_CURRENT.md`）。

## 生成的先后（`ThumbnailPlan`）

张数（中档）：30 分钟以内 60，30–60 分钟 90，1–2 小时 120，2–3 小时 180，更长 240。低档减半，高档加倍。
短片按「至少 3 秒一张」封顶：转码流约 5 秒才一个关键帧，再密取到的是同一帧。

顺序，设眼下播到 40%：

1. **附近**：40% 那一格与左右各两格，共 5 张；
2. **粗略预览**：24 张，均匀铺满全片，按对半细分的顺序做（片头、片尾、正中，再四分之一处……），做到哪一步全片都是均匀覆盖的；
3. **补全**：其余各格，同样按对半细分往里补。

不从 0% 排到 100%：那样刚打开的半分钟里只有片头有图。

悬停或拖到还没有图的地方，那几格插到队列最前。播放位置一下跳了 15 秒以上（拖动了），新位置附近的也插队。

悬停处没有精确的图时，用时刻最近的一张；但最多容许差一个粗略间隔（片长的 1/24），再远就只显示时间加一句「预览生成中 N%」，
不拿离得很远的图冒充。

## 不打扰主播放器

- 主播放器在起播、重连、缓冲、拖动后还没出画面时（`PlayerScreenState.needsBandwidth`），引擎不发起新的取帧，
  手上那一帧做完就停，状态显示「预览暂停，播放优先」；主播放器缓过来 0.8 秒后才继续。
- 默认一路。缓冲领先 20 秒以上或暂停着时才开第二路（只对转码流有用：取数据可以并行，解码是串行的）。
- 解码是软件解码、两个线程、跳过去块滤波：240 像素宽的图用不着显卡，也不与主播放器抢硬解。
- 网络这一层还有 SDK 自己的前后台优先级兜着。

## 黑帧

取到的帧平均亮度很低**且**亮度方差很小才算黑帧（夜景有亮处，方差不小，不算）。黑帧往后挪一点重取：
先 0.5、1、2 秒；取帧只能落在关键帧上，挪这么点常常还是同一帧，所以再挪 4、8 秒。换到过三张不同的帧仍是黑的，
就接受最初那张——真有黑场。

## 缓存

位置：数据目录的 `thumbnails/<指纹摘要>/`，便携版就在程序旁的 `data/thumbnails/`。

指纹：`gcid`（PikPak 的内容哈希）+ 文件大小 + 时长（取整到秒）+ 格式版本。不用播放地址（带签名，几小时就换）。
需求里写的是「fileId + 大小 + 修改时间 + 时长」；这里用 gcid 代替 fileId 与修改时间：gcid 是内容本身的哈希，
文件改名、挪目录都认得出，内容换了它一定变。本机文件没有 gcid，退回文件标识。

内容：

- `sheet-000.webp`、`sheet-001.webp`……每张 5×5 = 25 帧。第 n 格固定放在第 n/25 张的第 n%25 个位置，
  所以帧不按顺序生成也没关系，哪张添了新帧就重写哪张（每 3 秒把有变化的写一次）。
- `index.json`：

```json
{
  "version": 1,
  "fileId": "…",
  "durationMs": 7209000,
  "sourceFingerprint": "…",
  "width": 240, "height": 136,
  "columns": 5, "rows": 5,
  "slotCount": 180,
  "source": "480P 转码流",
  "frames": [ { "slot": 0, "timeMs": 20020, "sheet": 0, "x": 0, "y": 0 }, … ]
}
```

没做完就关了：已有的帧留着，下次打开接着做缺的。密度设置变了（格数不同）：这个视频的缓存重做。

上限：2 / 5 / 10 GB 或不限（默认 2 GB）。超出时按最近使用时间从最久没看的删起，正在看的不删。
一个两小时的视频约 0.5 MB，2 GB 能放几千个。

## 界面

- 悬停：气泡里上面是图、下面是时间。
- 拖动：按下后只更新预览与目标时间，松手才真正跳转。拖动中主画面跟不跟由「拖动进度条时跳转」决定：
  关 / 自适应（默认）/ 始终。自适应：每秒扫过进度条 8% 以内算慢拖，每 400 毫秒跟一次；扫得快就一次都不跳。
- 性能浮层（设置里开）：粗略 x/24、完整 x/N、来源、从网络读了多少、缓存多大。

## 验证了什么

- 引擎、调度、缓存、黑帧、让路、来源回退、中断续做：`thumbnail` 模块 39 个测试。
- **真解码**：测试里用程序自带的 libmpv 解码。没有 PikPak 账号拿不到真的转码流，所以测试自己合成了一条：
  真的 H.264（I_PCM 关键帧 + 全跳过的 P 帧）包在真的 MPEG-TS 里，每 5 秒一个关键帧、各段之间填充不等（码率不恒定）、
  每个关键帧一种颜色。测试按颜色核对「取到的这一帧确实是那个时刻的画面」，并核对每次读取都对齐到块。
- 界面：真的播放器控件、真的鼠标悬停事件，截图见构建目录的 `desktopApp/shots/`。
- 打好的程序包：`selftest.ps1` 的 `preview` 一项。

## 没有验证的

**对着 PikPak 真的转码流跑。** 合成流与真流的差别可能在：PAT / PMT 的写法、关键帧有没有随机访问标志、
每个关键帧前有没有带参数集、是不是 HEVC。应对：TS 这一路整个用不了时自动退到原画；关键帧两种认法都实现了；
H.264 与 HEVC 都认。拿到账号后先开性能浮层看「Thumb state」那一行写的来源是不是「转码流」。
