# 安全架构

PikSeek 的认证是独立实现的，与 Piko 的登录、凭据存储代码无关。这份文档说清边界在哪、机密怎么流动、
哪些保证有测试守着、哪些没有做到。

## 边界

```
主程序（界面、文件管理、播放器、PikPak SDK）
    │   只经 AuthService：login / session / refresh / logout / select / status
    │   拿到的只有 AuthSession = 账号名、用户 ID、访问令牌、到期时刻
    ▼
auth 模块（LocalAuthBroker）
    │   密码：只在登录那一下经过，用完清零，从不保存
    │   刷新令牌：只在这个模块里
    │   存储：DPAPI（当前 Windows 用户），存不了就不存
    ▼
PikPak 官方认证服务（白名单见 AUTH_ENDPOINTS.md）
```

- `auth` 模块不依赖 Piko 的任何代码，也不依赖 PikPak SDK；网络只用 JDK 自带的 `java.net.http`。
- 主程序这一侧，`PikoClientManager` 只负责在认证结果出来之后建、换 SDK 的 client。交给 SDK 的「密码来源」永远抛异常；
  SDK 的「会话存储」是 `BrokerSessionStore`，每次读都是向认证模块要一个可用的访问令牌，交回去的会话**不带刷新令牌**。
  所以 SDK 既登录不了，也刷新不了：登录与刷新会话的请求只从 `auth` 模块发出。
  （文件接口要的验证令牌由 SDK 自己向 `user.*` 要，请求里是公开算法算出的签名与用户 ID，没有密码与刷新令牌，
  见 `AUTH_ENDPOINTS.md` 末尾。）
- Piko 的这些文件已从代码里删掉，没有改名保留：`LoginState`、`LoginScreen`、`PikoSessionStore`、`DesktopSessionStore`、
  `SecretVault` / `LayeredVault` / `PlainFileVault`（明文兜底就在这里）、`PowerShellDpapiVault`、`MacKeychainVault`、
  `DpapiSecretVault`、`SecretServiceVault`、`DesktopCredentials`。`PikoClientManager` 是照新的边界重写的，里面没有密码。

### 为什么还在同一个进程里

需求里的首选是独立的 `AuthBroker.exe` 加命名管道。这一版是进程内的模块隔离，原因：访问令牌无论如何要进主进程
（SDK 发请求要用），拆进程能多隔开的只有刷新令牌与登录那一下的密码，而代价是两个进程的启动、管道的鉴权、
崩溃恢复与打包，对一个临时加的工具不划算。

接口是按「能拆」设计的：`AuthService` 的每个方法的参数与返回值都是可序列化的纯数据，没有回调、没有共享对象；
两个事件流（账号列表、要求重新登录）可以原样变成管道上的通知。拆的时候主程序不用改。

## 机密的生命周期

| 机密 | 在哪出现 | 存不存 | 说明 |
| --- | --- | --- | --- |
| 密码 | 登录页的输入框 → `CharArray` → 登录请求的请求体 | **从不保存** | 点登录的那一刻从输入框取走并清空输入框；`CharArray` 与请求体的字节用完清零。JVM 的 `String` 清不掉，所以密码只在拼 JSON 的那一下以 `String` 存在，不被任何字段引用 |
| 刷新令牌 | `auth` 模块的内存、DPAPI 密文 | 存，仅密文 | 不出 `auth` 模块。`AuthSession` 上没有这个字段（有测试用反射查） |
| 访问令牌 | `auth` 模块、主程序与 SDK 的内存、DPAPI 密文 | 存，仅密文 | 有效期约两小时 |
| 验证令牌 | 登录过程中的内存 | 不存 | 一次性 |
| 账号列表（账号名、昵称、头像地址、用量） | 内存、DPAPI 密文 | 存，仅密文 | 不是机密，但账号名是邮箱或手机号，同样只以密文落盘 |
| 直链（带签名的播放、下载地址） | 内存 | 不存 | 只在内存里留几分钟；不写日志、不进网络审计（审计只取主机名） |

日志里没有以上任何一样：认证相关的日志只写错误码、错误名与耗时。`PikoLog` 另有一层兜底脱敏。

## 存储：DPAPI，没有明文兜底

- `DpapiCredentialStore` 经 JDK 的 FFM 直调 `crypt32!CryptProtectData`，范围是 CurrentUser（没有 `LOCAL_MACHINE` 标志），
  带 `CRYPTPROTECT_UI_FORBIDDEN` 与一段固定的附加熵。密钥由 Windows 按登录用户保管，程序不持有任何密钥。
- 文件：`data/auth/accounts.dpapi`、`data/auth/session_<账号名的摘要>.dpapi`。文件名里没有账号名。
- 写入后读回、解密、逐字节比对，对不上就删掉并报错。
- **加密不了就不存**：DPAPI 不可用、写入失败、读回不一致，都不会改用别的方式保存。会话照常在内存里用到程序退出，
  登录页与安全页写明「仅本次运行有效」，下次启动重新登录。
- 刷新成功但新会话没能存下时，磁盘上的旧密文一并删掉：它里面的刷新令牌已被这次刷新作废。
- 解不开（换了 Windows 用户、换了电脑、文件被改过）一律当作「没有会话」，不存在「解不开就当明文读」的路。
  **所以把便携版整个文件夹拷到另一台电脑后，要在那台电脑上重新登录一次**，这是 DPAPI 的本意。

## 网络

- 认证模块：白名单、不跟随重定向、两道闸，见 `AUTH_ENDPOINTS.md`。
- 整个进程：没有遥测、统计、崩溃上报、广告；自动更新的代码（会联系 GitHub 与镜像站）已整个删掉。
- 网络审计（`NetworkAudit`）：进程默认的 `ProxySelector` 每建一条新连接都会被问一次，SDK 的 API 与 CDN 客户端、
  图片加载、认证模块都经过它，在那里记下目标主机名。只记主机名、用途与时刻。主播放器与缩略图引擎的 mpv 只读本机回环
  代理；万一退到让 mpv 直接读直链，也会把那个主机记进审计。
- 审计的局限：复用着的连接不会重复记，所以「最近」是最近一次**新建**连接的时刻；它记的是 Java 这一侧发起的连接，
  不是抓包。要做到抓包级别的核对，用系统防火墙或 Wireshark 对着 `PikSeek.exe` 看，结果应当与审计页一致。

## 能自己核对的地方

「设置 → 安全与隐私」里每一行都是当场查出来的，不是写死的文案：

| 显示的内容 | 怎么查出来的 |
| --- | --- |
| 会话保存：DPAPI / 未保存 | 问认证模块：存储自检通过、且没有账号的会话落在「只在内存」里 |
| 明文凭据文件：N 个 | 遍历数据目录，在文件内容里找 `access_token`、`refresh_token`、`password` 的键值与 JWT 的样子 |
| 遥测库：无 | 按类名在类路径上找 Sentry、Firebase、Amplitude、Mixpanel 等十几种 |
| 被白名单拦下的请求：N | 白名单的计数器 |
| 网络审计 | 见上 |

「导出安全报告」写出 `security-report.txt`，「导出网络审计」写出 `network-audit.txt`，写出前整份过一遍脱敏。

## 有测试守着的保证

`auth` 模块 32 个测试、`shared` 的 `SessionSmokeTest` 6 个，要点：

- 密码只出现在登录那一个请求里；登录后 `CharArray` 全是零；存储里找不到密码。
- 磁盘上的文件里找不到访问令牌、刷新令牌、账号名、密码（真的 DPAPI，真的文件）。
- 改一个字节的密文、或放一份明文冒充密文，读取都失败，不会被当成明文接受。
- 存储写不进去时：登录仍成功、状态报「只在内存」、存储里什么都没有、重启后要重新登录。
- 十六个并发请求在令牌过期时只触发一次刷新。
- 刷新被服务端拒绝：会话删掉、发出「要重新登录」、之后不再发请求。断网与 5xx：会话保留。
- 白名单外的地址（明文 HTTP、别的主机、仿冒的后缀、带端口、带用户名、别的路径）全部被拦，连传输层也拦。
- SDK 从不自己发 `/v1/auth/` 下的请求；它手里的会话的刷新令牌是空的。
- 与 SDK 的线上请求逐字段一致（`WireCompatibilityTest`）。

打好的程序包里还有一遍：`selftest.ps1` 的 `security` 一项，在裁剪过的运行时里重跑 DPAPI、白名单、遥测检查与明文扫描。

## 没有做到的

- **没有用真账号登录过**。开发机上没有 PikPak 账号。协议是照 SDK 的线上实现逐字段对齐的，但「对着真服务端登录成功」
  这一步要在有账号的机器上验。
- 独立进程的 AuthBroker：没有做，见上。
- 人机验证：服务端要求时只能报错，不能在程序里完成。可以改用刷新令牌登录。
- 访问令牌在主进程内存里：SDK 要用，避免不了。
- 进程内的其他代码（依赖库）理论上能通过反射读到认证模块的内存；进程隔离才能挡住这一点。
- 不防本机上以同一 Windows 用户运行的恶意程序：它可以调 DPAPI 解密（附加熵写在程序里，只能挡住不知情的程序）。
  这是 DPAPI CurrentUser 的固有边界。
